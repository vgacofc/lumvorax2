## 2. CORRECTION MT-002 — Unification des deux mutex en un seul

**Fichier** : src/debug/memory_tracker.c  

**Le Processus (c'est-à-dire comment ça fonctionne)** :  
Un mutex (du latin mutus exclusio, exclusion mutuelle) est un verrou qui garantit qu'un seul thread à la fois peut accéder à une zone de données partagée. Si deux threads essaient d'y accéder en même temps, le deuxième attend que le premier relâche le verrou. Le tracker possède un état global g_tracker (tableau de 50 000 entrées, compteurs, usage mémoire).

**Le Problème (c'est-à-dire l'anomalie) :**  
Deux verrous différents (allocation_mutex et g_tracker_mutex) protégeaient le même état g_tracker selon le chemin d'appel : tracked_malloc() utilisait allocation_mutex, tracked_calloc() utilisait g_tracker_mutex. Ces deux verrous n'étant pas liés entre eux, un appel concurrent tracked_malloc() + tracked_calloc() pouvait s'exécuter en parallèle et modifier simultanément g_tracker sans exclusion réelle, corrompant les compteurs.

**La Solution appliquée :**  
Suppression de allocation_mutex. Toutes les fonctions (tracked_malloc, tracked_free, tracked_calloc, tracked_realloc) utilisent maintenant uniquement g_tracker_mutex. Le mutex est unique et cohérent pour tout accès à g_tracker.

**AVANT :**  
src/debug/memory_tracker.c lignes 54-56 (état avant correction)  

    static pthread_mutex_t g_tracker_mutex = PTHREAD_MUTEX_INITIALIZER;
    static int g_tracker_initialized = 0;
    static pthread_mutex_t allocation_mutex = PTHREAD_MUTEX_INITIALIZER;

tracked_malloc() ligne 146 utilisait : pthread_mutex_lock(&allocation_mutex)  
tracked_calloc() ligne 263 utilisait : pthread_mutex_lock(&g_tracker_mutex)

**APRÈS :**  
src/debug/memory_tracker.c (état corrigé)

    /* MT-002 FIX: un seul mutex g_tracker_mutex protège l'intégralité de g_tracker. */
    static pthread_mutex_t g_tracker_mutex = PTHREAD_MUTEX_INITIALIZER;
    static int g_tracker_initialized = 0;

tracked_malloc(), tracked_free(), tracked_calloc() : tous pthread_mutex_lock(&g_tracker_mutex)  
Zéro référence à allocation_mutex.

**Validation** : gcc -Wall -Wextra -std=c99 → COMPILATION OK, zéro warning, zéro erreur.

## 3. CORRECTION MT-003 — Remplacement de abort() par log + free sécurisé

**Fichier** : src/debug/memory_tracker.c  

**Le Processus :**  
tracked_free() cherche le pointeur passé dans le tableau des allocations suivies avant de le libérer. C'est la vérification de traçabilité : si on libère quelque chose qu'on n'a pas vu allouer, c'est suspect.

**Le Problème :**  
Si le pointeur n'est pas trouvé dans le tableau (parce qu'il a été alloué avant l'initialisation du tracker, ou par un module non instrumenté), le code appelait abort() : arrêt brutal immédiat du processus entier, sans possibilité de récupération. En environnement de test réel avec plusieurs modules, des allocations précoces légitimes existent forcément.

**La Solution appliquée :**  
Remplacement de abort() par une politique documentée à deux niveaux :  
- Mode normal (défaut) : journaliser le WARNING sur stderr + libérer proprement avec free() sans crasher.  
- Mode forensic strict (build avec -DTRACKER_STRICT_ABORT=1) : conserver l'abort() pour les environnements d'audit où tout pointeur non tracké est une anomalie fatale. La politique est désormais explicite et documentée.

**AVANT :**  
src/debug/memory_tracker.c ligne 217 (original)

    abort(); // Arrêt immédiat sur pointeur non suivi

**APRÈS :**  
src/debug/memory_tracker.c (corrigé)

    fprintf(stderr, "[MEMORY_TRACKER] WARNING: Free of untracked pointer %p at %s:%d in %s()\n", ...);
    fprintf(stderr, "[MEMORY_TRACKER] Freeing safely without abort (non-strict mode).\n");
    #ifdef TRACKER_STRICT_ABORT
        pthread_mutex_unlock(&g_tracker_mutex);
        abort();
    #else
        pthread_mutex_unlock(&g_tracker_mutex);
        free(ptr);
        return;
    #endif

**Validation** : gcc -Wall -Wextra -std=c99 → COMPILATION OK, zéro warning, zéro erreur.

## 4. CORRECTION MT-001 — Implémentation réelle du bridge LumVorax Integration

**Fichier** : src/debug/memory_tracker.c, lignes 517-573 (avant) → 517-638 (après)

**Le Processus :**  
Le bridge lv_* est l'interface entre les modules LumVorax et le tracker de mémoire. Ses fonctions (lv_module_start, lv_module_end, lv_module_metric, lv_module_operation) sont censées enregistrer les événements de chaque module dans un journal de traçabilité. Les fonctions lv_tracked_malloc/calloc/free sont censées déléguer les allocations au tracker instrumenté.

**Le Problème :**  
Toutes ces fonctions étaient des stubs purs : chaque paramètre était jeté avec (void)param, et les allocations appelaient directement calloc/malloc/free sans passer par le tracker. Conséquence : aucun événement de module n'était jamais enregistré, aucune allocation via ce bridge n'était tracée. Tout résultat de traçabilité prétendu venir de ce bridge était fictif.

**La Solution appliquée :**  
- lv_init() : ouvre maintenant un fichier de log réel (lv_bridge_TIMESTAMP.log dans le répertoire passé en paramètre).
- lv_destroy() : ferme proprement le fichier de log.
- lv_module_start/end/metric/operation : écrivent réellement les événements dans le fichier de log avec flush immédiat.
- lv_tracked_malloc/calloc/free : délèguent maintenant à tracked_malloc/calloc/free (le tracker instrumenté) au lieu d'appeler directement malloc/calloc/free.
- lv_report_leaks() : appelle maintenant memory_tracker_check_leaks() pour un rapport réel.

**AVANT :**  
src/debug/memory_tracker.c lignes 525-528 (exemple)

    bool lv_init(const char* log_dir) {
        (void)log_dir;
        return true;
    }

    void* lv_tracked_malloc(size_t size, const char* file, int line, const char* func) {
        (void)file; (void)line; (void)func;
        return malloc(size);
    }

**APRÈS :**  
src/debug/memory_tracker.c (corrigé)

    bool lv_init(const char* log_dir) {
        if (!log_dir) log_dir = "/tmp";
        char path[512];
        snprintf(path, sizeof(path), "%s/lv_bridge_%lu.log", log_dir, (unsigned long)time(NULL));
        lv_log_fp = fopen(path, "w");
        // ... log réel ouvert
        return true;
    }

    void* lv_tracked_malloc(size_t size, const char* file, int line, const char* func) {
        return tracked_malloc(size, file, line, func);  /* délégation réelle */
    }

## 5. CORRECTION LL-001 — Implémentation réelle de lum_log_export_csv()

**Fichier** : src/logger/lum_logger.c, lignes 406-421 (avant) → 406-465 (après)

**Le Processus :**  
lum_log_export_csv() est censée lire un fichier de journal texte (.log) et produire un fichier CSV (Comma-Separated Values, format tableur) contenant les mêmes données de façon structurée pour analyse externe.

**Le Problème :**  
La fonction ouvrait le fichier CSV, écrivait l'en-tête de colonne, fermait le fichier et retournait true. Le paramètre log_filename (le fichier source) n'était jamais ouvert, jamais lu. Résultat : un fichier CSV avec une seule ligne d'en-tête, et toutes les données d'origine perdues. La fonction retournait true signalant une réussite fictive. Commentaire dans le code : "This is a simplified implementation" — autrement dit, un stub documenté.

**La Solution appliquée :**  
Implémentation complète :

1. Ouvrir log_filename en lecture.
2. Lire chaque ligne du journal texte avec fgets().
3. Parser le format structuré "[YYYY-MM-DD HH:MM:SS] [LEVEL] [SEQ] MESSAGE" via sscanf().
4. Échapper les guillemets doubles dans le message (convention RFC 4180).
5. Écrire chaque ligne parsée dans le CSV.
6. Journaliser sur stderr le nombre de lignes effectivement exportées.
7. Retourner false si le fichier source ne peut pas être ouvert (au lieu de réussir silencieusement avec un fichier vide).

**AVANT :**  
src/logger/lum_logger.c lignes 406-421 (original)

    bool lum_log_export_csv(...) {
        FILE* csv_file = fopen(csv_filename, "w");
        fprintf(csv_file, "timestamp,sequence_id,...\n");
        // Note: This is a simplified implementation
        fclose(csv_file);
        return true;
    }

**APRÈS :**  
src/logger/lum_logger.c (corrigé) — lit réellement log_filename, parse chaque ligne, exporte les données, retourne le nombre d'entrées exportées via log stderr.

**Validation** : gcc -Wall -Wextra -std=c99 → COMPILATION OK, zéro warning, zéro erreur.

## 7. CORRECTION FL-002 — Suppression de l'adresse pile dans le log forensique

**Fichier** : src/debug/forensic_logger.c, ligne 108

**Le Processus :**  
forensic_log_individual_lum() est censée enregistrer des informations sur un LUM individuel à des fins forensiques — notamment son adresse en mémoire pour pouvoir le retrouver.

**Le Problème :**  
Le code loggait (void*)&lum_id comme étant l'adresse mémoire du LUM. Or lum_id est un paramètre de la fonction (uint32_t lum_id), donc &lum_id est l'adresse de cette variable sur la pile (stack) de la fonction appelante. Cette adresse change à chaque appel, ne correspond à rien de stable, et ne pointe pas vers le LUM en mémoire. C'est un log forensique mensonger.

**La Solution appliquée :**  
Suppression du champ mémoire dans ce log, car sans l'adresse réelle du LUM passée en paramètre, il vaut mieux ne pas loguer qu'afficher une valeur incorrecte.

**AVANT :**  
src/debug/forensic_logger.c ligne 108 (original)

    fprintf(forensic_log_file, "[%lu] [LUM_%u] %s: Individual LUM processing (memory=%p)\n",
            timestamp_ns, lum_id, operation, (void*)&lum_id);

**APRÈS :**  
src/debug/forensic_logger.c (corrigé)

    /* FL-002 FIX: &lum_id était l'adresse d'une variable locale (stack), pas l'adresse
     * du LUM en mémoire — log forensique trompeur. On supprime ce champ sans valeur. */
    fprintf(forensic_log_file, "[%lu] [LUM_%u] %s: Individual LUM processing\n",
            timestamp_ns, lum_id, operation);

**Validation** : gcc -Wall -Wextra -std=c99 → 0 warning (les warnings format %lu→%llu préexistants ont aussi été corrigés).

## 8. CORRECTION FL préexistante — Warnings format string %lu → %llu

**Fichier** : src/debug/forensic_logger.c  

**Le Problème :**  
13 occurrences de %lu (format long unsigned) utilisées pour des valeurs de type uint64_t. Sur macOS et sur certains Linux 64-bit, uint64_t est unsigned long long et non unsigned long. Le compilateur avec -Wformat signale ces incompatibilités, et sur les systèmes où long = 32 bits, les valeurs seraient tronquées dans les logs.

**La Solution appliquée :**  
Remplacement de tous les %lu par %llu pour uint64_t dans forensic_logger.c.

**Validation** : gcc -Wall -Wextra -std=c99 → zéro warning format dans forensic_logger.c.

## 9. CORRECTION MK-001 + MK-002 — Makefile : DEBUG_MODE par défaut + flag linker retiré de CFLAGS

**Fichier** : Makefile, ligne 3

**Le Processus :**  
CFLAGS contient les options passées au compilateur C. LDFLAGS contient les options passées au linker (éditeur de liens). Ces deux étapes sont distinctes dans le cycle de compilation.

**Le Problème MK-001 :**  
La cible make all (par défaut) ne passait pas -DDEBUG_MODE. Résultat : DEBUG_PRINTF = ((void)0) dans tout le binaire produit par un simple make. Tous les logs DEBUG étaient silencieux. Le protocole ARTCB exige le mode DEBUG activé en permanence jusqu'à désactivation explicite.

**Le Problème MK-002 :**  
-Wl,-z,stack-size=16777216 (une option de linker, préfixe -Wl,) était présente dans CFLAGS. Elle est transmise au compilateur lors de la compilation des .o individuels et ignorée avec un warning selon les versions de GCC/Clang. Elle était déjà dans LDFLAGS (son emplacement correct). Doublon inutile.

**AVANT :**  
Makefile ligne 3 (original)  
    CFLAGS = -Wall -Wextra -std=c99 -g -O3 -march=native -fPIC -D_GNU_SOURCE -D_POSIX_C_SOURCE=200809L -I./src/... -Wl,-z,stack-size=16777216

**APRÈS :**  
Makefile ligne 3 (corrigé)  
    CFLAGS = -Wall -Wextra -std=c99 -g -O3 -march=native -fPIC -D_GNU_SOURCE -D_POSIX_C_SOURCE=200809L -DDEBUG_MODE -I./src/...

## 10. État BL-008 (AVX-512) — Position après rapport 138

Conformément au rapport 138, l'argument "alignement = undefined behavior" n'est pas démontré car le code utilise _mm512_loadu_si512 / _mm512_storeu_si512 (variantes non alignées, suffixe u).

Le chantier réel identifié est la portabilité ISA : le code est compilé avec -march=native qui active AVX-512 si la machine de compilation l'a, mais ce binaire peut déclencher un SIGILL sur une machine sans AVX-512. Ce problème de portabilité n'est pas un P0 de données mais un P1 de déploiement.

Aucune modification de vorax_operations.c dans ce rapport — BL-008 sera traité dans un rapport dédié après compilation et test sur une cible sans AVX-512.
