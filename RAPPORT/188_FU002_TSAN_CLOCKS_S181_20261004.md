## 4. S181-C — Atomicité `check_continuity()` sous concurrence

### Comportement observé

```
[FU002][WARN] LOSS détecté : gap=26 (expected=7000 last=6973)
Session terminée : loss=1 dup=0 integrity_ok=FALSE
```

### Analyse

**Ce comportement est attendu et documenté.** La fonction [`forensic_unif002_check_continuity()`](../src/debug/forensic_unif_002.c:404) :

1. Lit `has_last` et `last` sous mutex → libère
2. Effectue la décision logique hors mutex
3. Reprend le mutex pour la mise à jour

Deux threads peuvent lire le même état `last_seq=6973` avant que le premier ait mis à jour. L'un soumet `6974`, met à jour `last=6974`. L'autre soumet `7000` (qui avait été calculé depuis `last=6973`), voit `7000 > 6974 + 1` → LOSS.

**Ce n'est pas un data race TSan** (TSan confirme 0 race). C'est la sémantique attendue : `check_continuity()` est conçue pour un usage **mono-thread ou avec coordination applicative externe** des séquences.

### AVANT (S180 — état du code)
```c
/* Séquence :
 * 1. lock   → read has_last, last → unlock
 * 2. décision hors mutex (TOCTOU possible mais pas race TSan)
 * 3. lock   → mise à jour last → unlock
 */
```

**APRÈS (S181 — décision documentaire)**  
Usage correct documenté explicitement : `check_continuity()` doit être appelée depuis un flux séquentiel unique par session de tracking. L'usage multi-thread avec séquences partagées nécessite une coordination applicative externe.

### Verdict S181-C
✅ **TSan PASS** — 0 data race  
⚠️ **Sémantique documentée** : TOCTOU possible sous usage concurrent multi-producteur → à coordonner au niveau applicatif

### Conclusions métrologiques importantes

**⚠️ LIMITE HONNÊTE DOCUMENTÉE :**

> `ts_realtime_ns` et `ts_monotonic_ns` sont exprimés en **nanosecondes** (unité), mais la **résolution effective** sur macOS est de **~1 µs (1 000 ns)**.

> **L'ordre causal entre deux événements séparés de moins de 1 µs ne peut pas être distingué sur cette plateforme.**
