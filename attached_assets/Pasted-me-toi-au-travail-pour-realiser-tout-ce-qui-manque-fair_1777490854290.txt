## PARTIE 1 — L'anomalie A2 : métrique mal interprétée, pas bug

### Ce qui se passait

```
En mode PAGE-4KiB :
  lums_emitted  = 20 521
  bytes_dumped  = 84 054 016 (= 20 521 × 4096 octets parcourus)
  
  Relation : bytes_dumped = lums_emitted × 4096 ✅ cohérent

En mode BIT-1b :
  lums_emitted  = 672 432 128  (= 84 MiB × 8 bits)
  bytes_dumped  = 84 054 016   (IDENTIQUE au mode PAGE !)
  
  Apparence : bytes_dumped semble beaucoup trop bas
  → "Un seul octet par bit émis ? Bug !"
```

**La vraie signification de bytes_dumped :**

```
bytes_dumped = octets PARCOURUS en mémoire (source)
             = pages résidentes lues via pread()
             = CONSTANT quel que soit le mode

En PAGE : on lit 4096 octets → on écrit 1 lum_t de 64 octets
En BIT  : on lit 4096 octets → on écrit 4096 × 8 = 32 768 lum_t

bytes_dumped mesure l'INPUT (RAM lue)
lums_emitted mesure l'OUTPUT (LUMs générés)
→ Les deux sont cohérents, juste dans des espaces différents

C'est comme confondre la taille d'une vidéo source
avec la taille de ses sous-titres :
  Vidéo source = 10 GB (bytes_dumped)
  Sous-titres PAGE  = 1 KB (20 521 lum_t × 64B)
  Sous-titres BIT   = 3 GB (672M lum_t × 64B)
  La vidéo source ne change pas !
```

### Les 3 métriques C129 : système non-ambigu

```
AVANT C129 :
  2 métriques → confusion possible
  bytes_dumped = ???
  lums_emitted = ???

APRÈS C129 :
  3 métriques indépendantes et sémantiquement distinctes

  btc_c125_mem_bytes_dumped     = octets RAM parcourus (source)
                                  → mesure la COUVERTURE mémoire

  btc_c125_mem_lums_emitted     = nombre de LUMs générés (output format)
                                  → mesure la GRANULARITÉ choisie

  btc_c129_mem_file_size_bytes  = octets réellement écrits sur disque
                                  → mesure la TAILLE FICHIER .lum

Relation attendue en mode PAGE-4KiB :
  file_size = header(64) + lums_emitted × (64 + 4096) = header + lums × 4160
  → Arithmétique TMUL vérifiée

Relation attendue en mode BIT-1b :
  Si 1 LUM par bit (non-compact) :
  file_size = header(64) + lums_emitted × 64
  = 64 + 672M × 64 = 40.7 GiB

  Si bitmap compact :
  file_size = header(64) + bytes_dumped/8
  = 64 + 10.5 MiB ← léger

→ file_size_bytes discrimine entre les deux implémentations possibles
→ C'est exactement ce qu'on voulait mesurer
```

## PARTIE 2 — L'anomalie A3 : NUL padding décortiqué

### Ce que le fichier montre exactement

```
Fichier : btc_qm_engine_forensic_btc_20260428T225118Z_39163.log
Taille  : 110 592 octets = 27 × 4096

Structure observée :
  Octets 0 à 108430 : données texte valides (CSV métriques)
  Octet 108431       : premier NUL (0x00)
  Octets 108432 à 110591 : padding NUL

Ratio données réelles / padding :
  108 431 / 110 592 = 98.1% de données valides
  2 161 / 110 592  = 1.9% de NUL padding
```

### Cause identifiée : pré-allocation par blocs de 4096

```
Pattern ultra_forensic_logger :
  Le logger alloue/réserve l'espace par blocs de 4096 octets (= 1 page)
  pour éviter les réallocations fréquentes et fragmenter le FS

  Quand le run se termine :
  Bloc courant = partiellement rempli (données jusqu'à 108431)
  Le reste du bloc = non-initialisé = NUL si le fd a été ouvert O_CREAT

  Le fclose() ferme le fd SANS tronquer au contenu réel
  → 110592 - 108431 = 2161 octets de NUL restent dans le fichier

Analogie :
  Remplir un carnet de 27 pages en arrêtant au milieu de la 27ème
  Sans raturer le reste → les lignes vides semblent être du contenu vide
```

### Le fix C129-FIX-NUL-01 : ftruncate avant fclose

```c
/* Nouveau helper dans ultra_forensic_logger.c */
static void lv_truncate_file_to_current_pos(FILE* fp, const char* why) {
    if (!fp) return;
    fflush(fp);                          // Vide le buffer userspace → kernel
    long pos = ftell(fp);                // Position actuelle = taille réelle
    if (pos > 0) {
        int fd = fileno(fp);
        ftruncate(fd, (off_t)pos);       // Tronque au contenu réel
    }
    /* Log optionnel */
    if (why) fprintf(stderr, "[LUM-TRUNCATE] %s at pos=%ld\n", why, ftell(fp));
    fclose(fp);
}

/* Appelé dans les 3 scénarios de fermeture : */
// 1. Rotation (cap 20 MB atteint)
// 2. Switch module
// 3. destroy() en fin de run

/* Résultat : 0 NUL dans les fichiers .log produits */
```

**Pourquoi ftruncate est la bonne approche :**
```
Alternative 1 : Ne pas pré-allouer
  → Fragmentation du FS, ralentissements sur SSD avec jitter
  → Non recommandé pour les logs haute fréquence

Alternative 2 : Marquer la fin avec un sentinel
  → Ajoute de la complexité au parseur
  → Risque de confusion si le sentinel apparaît dans les données

ftruncate() :
  → Opération atomique kernel (1 syscall)
  → Ne déplace pas les données existantes
  → Le FS met à jour la taille sans toucher le contenu
  → Parseur peut lire jusqu'à EOF naturellement
  → Coût : ~1 µs (négligeable vs le fclose lui-même)
```

### Le test minimal requis

```c
/* Test unitaire à implémenter en C130 */

// Étape 1 : Allouer et remplir une zone contrôlée
uint8_t buf[16384];
for (int i = 0; i < 16384; i++) {
    buf[i] = (uint8_t)(i * 37 + 13);  // Pattern déterministe non-trivial
}

// Étape 2 : Snapshot BIT-level de cette zone
lum_memory_snapshot_buffer(buf, 16384, "test_bit_level.lum",
                            LUM_TRACE_GRANULARITY_BIT);

// Étape 3 : Modifier la zone (simulation d'un run)
// (optionnel pour le test minimal)

// Étape 4 : Reconstruire depuis le .lum
uint8_t reconstructed[16384];
lum_memory_reconstruct("test_bit_level.lum", reconstructed, 16384, NULL);

// Étape 5 : Vérifier diff=0 bit à bit
uint64_t diff_bits = 0;
for (int i = 0; i < 16384; i++) {
    diff_bits += __builtin_popcount(buf[i] ^ reconstructed[i]);
}
printf("diff_bits = %lu (expected: 0)\n", diff_bits);
assert(diff_bits == 0);  // ← PREUVE

// Vérification SHA-256 pour robustesse
assert(sha256(buf, 16384) == sha256(reconstructed, 16384));
```

**Pourquoi ce test sur buffer fixe et non "self process" :**
```
Self process snapshot = DIFFICILE à tester pour diff=0 :
  La mémoire process change entre le snapshot et la comparaison
  (timestamps, compteurs, registres, stack frames)
  → Le diff ne serait jamais exactement 0 même si LUM est correct

Buffer fixe = CORRECT pour prouver BIT-1b :
  Le buffer ne change pas entre snapshot et comparaison
  diff=0 prouve que LUM lit et reconstruit fidèlement
  → C'est la preuve falsifiable demandée
```

### Q3 — Thread dédié pour snapshot BIT : conception

```
Problème : snapshot BIT-1b sur 84 MiB = 672M LUMs × 64B = 40.7 GiB
  Durée estimée : 40.7 GiB / (438 MiB/s) ≈ 95 secondes de blocage

Solution : thread dédié non-bloquant

Architecture proposée :

Thread principal (mining) :
  Signal au thread snapshot : "commence le snapshot"
  Continue le mining pendant ce temps

Thread snapshot (dédié) :
  Ouvre /proc/self/mem en mode non-bloquant
  Snapshot en streaming (écrit au fil de la lecture)
  Signal au thread principal : "snapshot terminé"
  → Aucun blocage du mining

Synchronisation :
  atomic_bool g_snapshot_in_progress = false;
  → Mining ignore les pages modifiées pendant le snapshot
  → Cohérence partielle acceptable (pas de copy-on-write)

Taille fichier avec thread dédié :
  Même taille mais écrit en 95s de façon asynchrone
  Le mining continue à 8.94 MH/s pendant ce temps
```

**Q4 — Taille BIT-1b : résoudre la tension 40 GiB vs 10.5 MiB**

```
Deux implémentations possibles de BIT-1b :

Option A — 1 LUM par bit (non-compact) :
  672M bits × 64 octets = 40.7 GiB
  Avantage : format uniforme (même parseur que PAGE)
  Inconvénient : 40 GiB impraticable sur laptop

Option B — Bitmap compact (1 bit/bit) :
  84 MiB source / 8 = 10.5 MiB de bitmap
  + header TMUL 64 octets
  = 10.5 MiB fichier .lum ← LÉGER
  Avantage : compact, rapide, réaliste
  Inconvénient : parseur différent de PAGE/BYTE

Recommandation C130 :
  Implémenter Option B pour le mode BIT-1b
  Format : header TMUL 64o + bitmap 10.5 MiB (1 bit = présence/absence)
  + Section optionnelle : checksum par page (1 uint32 par page = 80 KiB)

  Total : 64 + 10.5 MiB + 80 KiB ≈ 10.6 MiB ← parfaitement praticable
  Snapshot en : 10.6 MiB / 438 MiB/s ≈ 24 ms (vs 192 ms pour PAGE)
```
