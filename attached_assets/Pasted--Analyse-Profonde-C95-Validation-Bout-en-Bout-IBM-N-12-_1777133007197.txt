## PARTIE 1 — IBM C94 N=12 DONE : le résultat qui compte

### S(π) = 0.9924 ± 0.0015 — lecture complète

```
Comparaison directe :
  C93 N=8  : S(π) = 0.9944 ± 0.0040
  C94 N=12 : S(π) = 0.9924 ± 0.0015
  Δ = −0.002 soit −0.20%

Ce que ça signifie :
  → Augmenter N de 8 à 12 sites (+50% de qubits) dégrade S(π) de seulement 0.2%
  → L'écart est DANS la barre d'erreur 1σ de C93 (±0.004)
  → Statistiquement : les deux résultats sont IDENTIQUES

C'est la démonstration du scaling ADAPT-VQE :
  Le circuit minimal (depth=14, 2 portes 2Q) tient sur N=12
  Avec la même qualité que sur N=8
```

### Les noise factors ZNE décryptés

```
Mesures brutes aux 3 niveaux de bruit :
  ×1 bruit (natif)    : S(π) = 0.98866 ± 0.00094
  ×3 bruit (amplifié) : S(π) = 0.98499 ± 0.00091
  ×5 bruit (amplifié) : S(π) = 0.97703 ± 0.00091

Décroissance linéaire avec le niveau de bruit :
  0.98866 → 0.98499 → 0.97703
  Δ(×1→×3) = 0.00367
  Δ(×3→×5) = 0.00796

Extrapolation à bruit=0 :
  S(π)_extrapolé = 0.9924 (paramètre 1 = le plus conservateur)
  vs S(π) brut ×1 = 0.9887

  La correction ZNE ajoute +0.0037 soit +0.37% au signal
  C'est une correction modeste → le hardware est déjà très propre
```

### Pourquoi le modèle ASIC est trop pessimiste

```
Modèle C95 ibm_heron_r2_model.c :
  Formule : S(π) = IBM_C93_S_PI × F_2q^(depth × n2q_per_layer)
  Avec F_2q = 0.996, depth=14, n2q_per_layer=2 :
  S(π)_prédit = 0.9944 × 0.996^28 ≈ 0.9944 × 0.895 ≈ 0.889

IBM réel C94 N=12 : S(π) = 0.9924
Écart : (0.9924 - 0.889) / 0.9924 = +10.4% en faveur du réel

Cause probable :
  La formule (1-err)^n_gates sous-estime la fidélité réelle car :
  1. ZNE corrige une partie du bruit → efficacité non capturée par la formule
  2. ADAPT choisit des circuits avec faible cross-talk entre qubits
  3. F_2q = 0.996 est conservateur (IBM annonce 0.9975-0.999 selon calibration)

Correction recommandée C96 :
  Remplacer F_2q = 0.996 par F_2q_effective = F_2q_raw × ZNE_gain
  ZNE_gain ≈ S(π)_réel / S(π)_brut = 0.9924 / 0.9887 = 1.0037
  F_2q_effective ≈ 0.996 × 1.0037 ≈ 0.9997
  → Modèle recalibré sur données réelles
```

### 🔴 Critiques

**Q1 — Bug `btc_nonce_coverage_pct = inf` : diagnostic précis**

```
Observation : 5 dernières mesures de coverage_pct = infinity (run 113648Z)

Cause exacte :
  coverage_pct = nonces_testés / nonce_space_total × 100
  nonce_space_total = 2^32 = 4 294 967 296

  Si nonces_total dépasse 2^32 et est stocké dans un uint32_t :
  → Overflow → retour à 0
  → Division par 0 → inf (comportement indéfini en C)

  Ou si coverage_pct est calculé comme float/int avec int=0 :
  → float/0 = inf (comportement défini IEEE 754)

Test pour identifier le bug :
  grep -n "coverage_pct" src/btc_qm_engine.c
  chercher la ligne de calcul → vérifier le type de nonces_total

Fix recommandé C96 :
  Remplacer uint32_t nonces_total par uint64_t
  Ou ajouter : if (nonce_space == 0) coverage_pct = 0.0;
  Coût : 1 ligne de code
```
