## PARTIE 1 — Le score VORAX : comprendre le nouveau sélecteur ADAPT

### La formule du score VORAX décortiquée

```
score_VORAX(opérateur k, couche l) = 
    w_grad × |gradient_k|
  + w_stab / (1 + curv_k)
  - w_depth × max(0, depth_after_k − 14)

Terme 1 : w_grad × |gradient_k|
  → Récompense les opérateurs qui font le plus changer l'énergie
  → |gradient| élevé = opérateur pertinent pour ce Hamiltonien
  → C'est le critère ADAPT classique

Terme 2 : w_stab / (1 + curv_k)
  → Récompense la stabilité au voisinage de θ optimal
  → curv_k = courbure de E(θ) au point optimal = |d²E/dθ²|
  → Courbure faible = paysage plat = solution stable
  → Courbure élevée = paysage raide = solution fragile (sensible au bruit)
  → Ce terme est NOUVEAU par rapport à ADAPT standard

Terme 3 : -w_depth × max(0, depth_after_k − 14)
  → Pénalise les opérateurs qui dépassent depth_phys = 14 (seuil C93)
  → Tant que depth_after ≤ 14 : pénalité = 0 (ici depth=5, jamais pénalisé)
  → Ancre explicite sur la mesure IBM réelle C93

Poids utilisés : w_grad, w_stab, w_depth (non spécifiés dans le rapport)
  → Le rapport montre que w_stab domine après la couche 0
  → Ce qui signifie w_stab >> w_grad en valeur effective
```

### Les gradients croissants : signature d'un état Néel qui s'ouvre

```
Gradients successifs : 0.0250 → 0.0374 → 0.0497 → 0.0619
  Ratio : chaque gradient ≈ 1.25× le précédent

Signification physique :
  L'initialisation Néel |010101010101⟩ est l'état le plus corrélé possible
  → Chaque couche RXX(i=1) augmente la profondeur de la corrélation
  → Plus le circuit est profond, plus le gradient suivant est fort
  → C'est une convergence monotone et stable

Analogie :
  C'est comme pousser une bille au fond d'une cuvette.
  Plus la bille est près du fond, plus la force de rappel est forte.
  Ici : plus le circuit est proche de l'état optimal,
         plus le gradient de l'opérateur suivant est grand.
```

### Scores VORAX successifs : 0.0394 → 0.3374 → 0.3497 → 0.3619

```
Saut majeur entre couche 0 et couche 1 : 0.0394 → 0.3374 (+755%)
Ensuite : croissance lente (+3.6%, +3.5%)

Interprétation :
  Couche 0 : le terme w_stab/(1+curv) est petit (état initial Néel = courbure élevée)
             le gradient 0.025 domine → score faible = 0.0394
  
  Couche 1 : après RXX(i=1), la courbure diminue (état plus plat)
             w_stab/(1+curv) saute → score = 0.3374
  
  Couches 2-3 : raffinement progressif, w_stab continue de croître légèrement
             scores 0.3497 et 0.3619

Conclusion : le score VORAX converge en 4 couches parce que l'état Néel + RXX
             est naturellement le circuit minimal pour N=12 Hubbard AFM.
```

## PARTIE 2 — 4 × RXX(i=1) : monotonie ou physique ?

### Pourquoi le même opérateur est choisi 4 fois

```
Pool disponible : {RXX, RYY, RZZ} × {paires (i, i+1) pour i=0..10}
= 3 types × 11 paires = 33 opérateurs candidats

Opérateur gagnant à chaque couche : RXX(i=1)

Pourquoi RXX et pas RYY ou RZZ ?
  Hamiltonien Hubbard JW → terme de hopping = (XX + YY)/2
  Pour état Néel |↓↑↓↑...⟩ = |010101...⟩ :
    RXX(i=1) agit exactement sur la paire (0,1) qui est la
    paire (↓,↑) la plus déséquilibrée → gradient maximal
  RYY a gradient similaire mais score_stab légèrement inférieur
  RZZ agit sur les occupations (ZZ) → gradient faible depuis Néel

Pourquoi le site i=1 et pas i=3, i=5... ?
  Convention d'indexation Qiskit : le site "le plus excité"
  depuis Néel standard est i=1 dans la chaîne JW-spinless
  Les autres sites ont des gradients quasi-identiques
  mais le score de stabilité (w_stab) favorise i=1 de justesse
```

### Est-ce physiquement correct ou un artefact ?

```
Cas N=8 (C93) : ADAPT avait aussi choisi RXX dominant
  depth_phys = 14, 2 portes 2Q → signal S(π) = 0.9944

Cas N=12 (C94) : 4 × RXX(i=1), depth_after = 5
  Moins de portes 2Q que C93 pour un N plus grand
  → Soit le circuit N=12 est vraiment plus simple à préparer
  → Soit le score VORAX sur-simplifie pour N=12

Physique Hubbard 1D :
  État fondamental N=12 demi-remplissage = superposition Néel + fluctuations
  4 couches de RXX sur UN seul site ne capturent que les corrélations locales
  Les corrélations longue portée (C(r) pour r=5,6) nécessitent des RXX(i=5) etc.

→ La monotonie 4×RXX(i=1) est probablement un artefact de l'initialisation Néel
  qui rend le site i=1 artificellement dominant
→ Le --diversity_penalty prévu en C95 est nécessaire pour explorer le pool complet
```

## PARTIE 3 — Le wrapper C triple fallback : analyse technique

### La logique `__has_include` expliquée

```c
#if __has_include("chemin_absolu/ibm_quantum_constants.h")
    // Cas 1 : build depuis racine projet (Makefile standard)
    // → Le header maître est trouvé via chemin relatif depuis racine
    #include "chemin_absolu/ibm_quantum_constants.h"

#elif __has_include("ibm_quantum_constants.h")
    // Cas 2 : build depuis le sous-répertoire
    // → Le header est dans le même répertoire include/
    #include "ibm_quantum_constants.h"

#else
    // Cas 3 : build isolé (tests unitaires, CI partielle)
    // → Valeurs minimales hardcodées pour éviter l'échec de compilation
    #define IBM_C93_S_PI       0.9944
    #define IBM_C93_DEPTH_PHYS 14
    #define IBM_C93_N2Q_PHYS   2

#endif
#define LUMVORAX_C94_IBM_BRIDGE 1   // Sentinelle : propagation active
```

**Pourquoi `__has_include` est la bonne approche :**
```
Alternatives possibles et leurs problèmes :
  -I flag Makefile : nécessite de modifier chaque Makefile de chaque sous-projet
  #include absolu   : casse si le projet est cloné dans un autre répertoire
  env variable      : nécessite que l'environnement soit configuré

__has_include :
  → Résolution à la compilation, pas au link
  → Portable C11/C++17, supporté par gcc et clang
  → Zero modification des Makefiles existants
  → Dégradation gracieuse (fallback) si le header n'est pas trouvé
  → Exactement le bon outil pour propager dans un arbre source hétérogène
```

### Ce que le smoke test valide réellement

```
[smoke] ibm_normalize_signal_strength(0.5, 8) = 0.50281

Formule : s_local / IBM_C93_S_PI = 0.5 / 0.9944 = 0.50281 ✅

Ce que ça signifie pour un module classique :
  Si VORAX kernel prédit une corrélation s_local = 0.5
  Et que IBM a mesuré IBM_C93_S_PI = 0.9944 pour le même type de système
  → L'écart normalisé = 0.50281 = "le solveur classique est à 50% du QPU"

  Si s_local = 0.99 → normalisé = 0.99557 ≈ 1.0 → "le solveur égale le QPU"

Utilisation prévue en C95 dans vorax_kernel_refine_gradient_aware() :
  double residual = ibm_normalize_signal_strength(vorax_pred_s_pi, N) - 1.0;
  loss += gamma * residual * residual;  // pénalité si loin du QPU
```

**Q3 — Pourquoi S(π) stdout = +0.999 en dry-run mais sans barres d'erreur ?**


**Q4 — Le --diversity_penalty : formule recommandée**

```
Pour casser la monotonie 4×RXX(i=1) sans perdre l'efficacité :

score_VORAX_diversifié = score_VORAX + diversity_penalty(k, history)

diversity_penalty(k, history) = -α × count(op_k in history_last_m_layers)

Exemple avec α=0.1, m=2 :
  Couche 3 : RXX(i=1) a déjà été choisi 2 fois dans les 2 dernières couches
  → pénalité = -0.1 × 2 = -0.2
  → Favorise RXX(i=3) ou RYY(i=1) comme alternative

Valeurs recommandées pour N=12 :
  α = 0.05-0.15 (à calibrer en AER)
  m = 2 (ne pénalise que les 2 dernières couches)

À tester en dry-run AER avant tout submit IBM :
  python tools/ibm_quantum_runner_c94.py --N 12 --backend aer
          --diversity_penalty 0.1 --measure_final
```
