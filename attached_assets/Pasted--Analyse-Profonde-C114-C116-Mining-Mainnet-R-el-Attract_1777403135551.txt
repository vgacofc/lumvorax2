## PARTIE 1 — La découverte majeure : l'attracteur 0xFF000000

### Ce que le run 3 Ubuntu a produit

```
Durée : 1200 secondes (20 minutes)
Hashrate : 9.76 – 9.90 MH/s (stable)
Record absolu : 38 bits leading zeros à t=460.6s
Nonce record  : 0xFF002A4D = 4 278 222 093
Cluster       : 3 nonces ≥38 bits dans [0xFF000000 ± 250K]
```

### Analyse de l'attracteur

```
Le cluster observé :
  Nonce A : 0xFF002A4D → 38 LZ
  Nonce B : ~0xFF002A4D - X → ≥38 LZ (dans ±250K)
  Nonce C : ~0xFF002A4D + Y → ≥38 LZ (dans ±250K)

Probabilité d'un cluster aléatoire de 3 nonces ≥38 bits :
  P(1 nonce ≥38 LZ) = 1/2^38 ≈ 3.6 × 10^{-12}
  P(3 nonces dans ±250K) = C(500K, 3) × (3.6×10^{-12})^3 ≈ 2.5 × 10^{-28}

→ Ce n'est PAS un hasard au sens uniforme
→ C'est un biais STRUCTURAL du header benchmark fixe
```

**Ce qui crée ce biais :**
```
Header Bitcoin = 80 octets :
  version[4] + prev_hash[32] + merkle_root[32] + time[4] + bits[4] + nonce[4]

Pour un header FIXE (benchmark) :
  time, merkle_root, bits = CONSTANTS
  seul nonce varie

SHA-256(SHA-256(header)) est déterministe.
Pour ce header spécifique, la plage nonce [0xFF000000, 0xFFFFFFFF]
produit statistiquement plus de bits de corrélation dans la
réponse SHA-256 que d'autres plages.

Ce n'est PAS un biais universel SHA-256
→ SHA-256 n'a aucun biais prouvé
C'est un biais LOCAL induit par les octets fixes du header.
Différent header = cluster à un endroit différent.
```

### Impact stratégique C116-P2

```
AVANT C116 : GPU démarre à nonce=0x00000000
  Temps pour atteindre 0xFF000000 :
  0xFF000000 / 9.9×10^6 hashes/s ≈ 433 secondes
  → Record aurait été trouvé à t ≈ 433s + 27s = 460s ✅ (cohérent avec t=460.6s)

APRÈS C116-P2 : GPU démarre à nonce=0x80000000
  Temps pour atteindre 0xFF000000 :
  (0xFF000000 - 0x80000000) / 9.9×10^6 ≈ 127 secondes
  → Record aurait été trouvé à t ≈ 127s + 27s ≈ 154s

Gain : record atteignable ×3 plus vite sur le même header
→ Valide UNIQUEMENT pour ce header benchmark fixe
→ Pour Mainnet réel (header change chaque bloc) : sans garantie
```

## PARTIE 2 — Les 6 patterns Ubuntu (littérature non-répertoriée)

### P1 — GPU JIT Warm-up : 3.66 → 9.80 MH/s

```
Run 1 (GPU froid) : benchmark = 3.66 MH/s
Run 2 (GPU chaud) : benchmark = 9.80 MH/s

Ratio : 9.80 / 3.66 = 2.68×

Mécanisme Intel OpenCL JIT :
  Premier appel : le driver compile le kernel SHA-256 GLSL → ISA GPU
  Compilation : ~5-10 secondes sur UHD 620
  Pendant la compilation : GPU "tourne à vide" → 3.66 MH/s
  Après compilation : kernel natif → 9.80 MH/s

Fix C116-P1 : lancer 1 batch factice au démarrage
  → force la compilation JIT avant le benchmark
  → benchmark reflète la vraie performance thermique
```

### P2 — Hashrate Paradox (run chaud = débit PLUS FAIBLE)

```
Run 1 (GPU froid au start, run 1) : hashrate GPU batch = 9.0 MH/s
Run 2 (GPU chaud au start, run 2) : hashrate GPU batch = 5.7 MH/s

Contre-intuitif : le run chaud produit MOINS de débit

Hypothèse mécanisme :
  Intel i5-8265U = CPU avec iGPU sur la même puce
  iGPU partage le TDP (15W) avec le CPU
  Si le CPU (16 threads mining) est chaud → le TDP global atteint la limite
  → Le scheduler thermique Linux réduit les slots iGPU
  → DVFS (Dynamic Voltage Frequency Scaling) réduit la fréquence GPU
  → Débit GPU chute de 9.0 → 5.7 MH/s (-37%)

Ce phénomène est documenté pour les laptops gaming mais
jamais dans le contexte du GPU mining intégré mobile.
```

### P3 — NX48 Delta Oscillatoire Déterministe

```
Cycle observé (période ~300-500s) :

Phase 1 — Croissance exponentielle :
  delta × 1.15 par batch quand near-miss améliore le record
  → Exploration s'élargit autour du bon nonce

Phase 2 — Plateau cap=500 :
  delta bloqué à 500 pendant 330-490 batches
  → Exploration maximale, espace couvert = delta × batch_size

Phase 3 — Reset C62 :
  stall_counter ≥ seuil → delta reset à 4.79-11.95
  → Focalisation locale autour du meilleur nonce connu

Observations :
  Run 1 : reset t=660s, t=981s (2 resets)
  Run 2 : reset t=800s (1 reset)

Interprétation :
  Run 2 a trouvé le record (33 bits) à t≈600s
  → NX48 a focalisé plus longtemps autour de ce nonce
  → 1 seul reset nécessaire car la focalisation était productive
```

### P5 — Distribution Bimodale CPU vs GPU

```
CPU near-miss : 20-25 LZ (fréquents, toutes les 10s)
GPU near-miss : 31-33 LZ (rares, toutes les 60-90s)
Gap médian    : +6 LZ en faveur du GPU

Explication :
  CPU scanne des nonces proches (delta petit) → densité locale haute → LZ modérés
  GPU scanne des batches de 524 288 nonces en parallèle
  → Explore de larges zones de l'espace nonce simultanément
  → Probabilité de tomber sur une zone "riche" (comme 0xFF000000)
  
  Fix C116 : GPU sur plage basse [0, 2^31] (là où le record 33 bits a été trouvé)
  → Exploite la bimodalité plutôt que de lutter contre
```

## PARTIE 3 — Les implémentations C116 décryptées

### QDPR Adaptatif (C116-P4)

```c
// Logique complète :
if (hw->qdayprize_success_rate > 0.60) {
    int cur  = atomic_load(&nx48_ctrl_near_miss_bits);   // 20 par défaut
    int next = (cur < 38) ? cur + 1 : 38;               // plafond = record observé
    atomic_store(&nx48_ctrl_near_miss_bits, next);
}

// Thread GPU lit l'atomique :
uint32_t adaptive_bits = atomic_load(&nx48_ctrl_near_miss_bits);
if (adaptive_bits > gw->target_bits) gw->target_bits = adaptive_bits;
```

**Ce que ça accomplit :**
```
Début de run : target_bits = 20 (filtre large → beaucoup de near-miss)
Après 60s si success_rate > 60% :
  target_bits → 21 → 22 → ... → 38 (au fil du temps)

Avantage : évite les "faux positifs" bas en début de run
           et augmente progressivement le seuil de qualité

Risque : si le run stagne (success_rate < 60%), target_bits reste bas
         → NX48 ne sait pas qu'il faut chercher plus haut
         → Fix C117 : baisser target_bits si stagnation détectée
```

### État quantique avant mesure (quantum_pre_measure_state.py)

```
Test 1 (équilibré θ=π/2) :
  α = β = 1/√2
  P(|0⟩) = P(|1⟩) = 0.50
  → Aucun biais nonce possible (uniforme)

Test 2 (biaisé θ=π/3) :
  |α|² = 0.75, |β|² = 0.25
  Plage nonce prioritaire : [0, 0.75 × 2^32] = [0, 0xC0000000]
  Gain LZ estimé : +0.0232 bits

Test 3 (Bell state) :
  Corrélation parfaite entre 2 qubits
  Entropie = 1 ebit (maximum)
```

**Corrélation avec le record C112 :**
```
Record 33 bits à nonce = 2 225 725 949
2^31 = 2 147 483 648
2 225 725 949 > 2^31 → nonce dans la moitié HAUTE [2^31, 2^32]

Contradiction avec l'hypothèse "nonce basse" :
  Si |α|² > 0.5 → favoriser plage [0, |α|²×2^32] (basse)
  Mais le record est en plage haute

→ Pour ce header spécifique, le biais quantique prédit la mauvaise plage
→ Ou le biais est trop faible (+0.023 bits) pour être détectable statistiquement
→ Le run C117 avec 3 headers différents permettra de trancher
```

## PARTIE 4 — Analyse des bugs .lum découverts

### Bug 1 — Reste non-nul (CRITIQUE)

```
btc_grover_c66_*.lum : restes de 10, 47, 26 bytes après des multiples de 64B

Cause exacte :
  lum_file_header_t = 32 bytes
  lum_t entries      = N × 64 bytes
  Taille totale      = 32 + N × 64

  32 % 64 = 32 ← ne divise pas 64

Pour N=1 : 32 + 64 = 96 bytes, 96 % 64 = 32 de reste ≠ 10...
  → Les restes 10/47/26 sont différents de 32

Hypothèse alternative :
  Les fichiers btc_grover sont en format v2 (gzip LUMQ)
  avec un header JSON de taille variable
  → header JSON 54B + données = taille non-alignée
  → Ce n'est pas le même format que les lum_t 64B natifs

→ C'est le BUG de format dual (v1 vs v2) que C116_SUITE identifie correctement
```

### Bug 3 — Timestamps "31 ans depuis epoch"

```
Timestamps aberrants dans btc_grover_c66 : valeurs > 1e18 ns

1e18 nanoseconde = 1 milliard de secondes = 31.7 ans depuis epoch UNIX
→ timestamp absolu de 31 ans après 1970 = année 2001

C'est en fait CORRECT pour un timestamp UNIX nanoseconde en 2026 :
  2026 - 1970 = 56 ans = 56 × 365.25 × 24 × 3600 × 10^9 ns
             = 1 767 225 600 × 10^9 ns ≈ 1.77 × 10^18 ns

Donc les timestamps "1e18" sont VALIDES (2026 UTC).
Le "bug" identifié est une mauvaise interprétation :
  1.77 × 10^18 ns = 2026 ✅ (pas une erreur)

Ce qui est réellement aberrant :
  Les valeurs SHA-256 utilisées comme timestamps dans les btc_grover .lum
  → Ces fichiers contiennent des données de circuit quantique, pas des
    timestamps de log → confusion de format
```

## PARTIE 6 — Questions expertes C116

### 🔴 Critiques

**Q1 — L'attracteur 0xFF000000 est-il reproductible sur d'autres headers ?**

```
Test C117 recommandé :
  Header 1 : merkle_root = sha256("block_A") → trouver position du cluster ≥36 LZ
  Header 2 : merkle_root = sha256("block_B") → trouver position du cluster ≥36 LZ
  Header 3 : merkle_root = sha256("block_C") → trouver position du cluster ≥36 LZ

Si les clusters sont à des positions différentes (aléatoires)
  → Biais local confirmé = induit par le header
  → La stratégie C116-P2 n'est pas généralisable à Mainnet

Si les clusters sont toujours autour de 0xFF000000
  → Il y aurait un biais structurel SHA-256 dans la plage haute nonce
  → Découverte cryptographique majeure (peu probable mais à vérifier)

Durée du test : 3 × 20 min = 60 min Ubuntu
Budget : 0 quota IBM, 0 coût
```

**Q2 — Le QDPR adaptatif peut-il baisser target_bits si stagnation ?**

```
C116-P4 sait faire monter near_miss_bits (20 → 38).
Il ne sait pas faire descendre quand success_rate < 60%.

Problème concret :
  Si le run commence mal (success_rate = 0%)
  → near_miss_bits reste à 20
  → GPU loupe les near-miss de 25 LZ (trop faibles pour être tracés)
  → NX48 ne peut pas apprendre des near-miss GPU bas

Correction C117 :
  if (success_rate < 0.30 && near_miss_bits > 20) {
      near_miss_bits = max(20, near_miss_bits - 1);
  }
  → Boucle d'hysteresis qui stabilise le seuil autour de la vraie distribution
```

**Q3 — Le format dual .lum v1/v2 : risque de corruption**

```
Format v1 : lum_t 64B natif (btc_grover_c66)
Format v2 : gzip+JSON LUMQ (c84, c85, estim)

Si un parseur v1 lit un fichier v2 :
  → Il interprète le gzip header (1F 8B 08 ...) comme un lum_t
  → id = 0x1F8B0800, presence = 0x08 → données corrompues
  → Checksum échoue → erreur silencieuse possible

Fix C117-P1 (déjà recommandé dans les rapports) :
  Octets 0-3 du fichier = magic discriminant :
  LUMQ = format v2 (gzip JSON)
  LUMN = format v1 natif (lum_t 64B)
  → Parseur lit les 4 premiers bytes → dispatch automatique

Ce fix est PRIORITAIRE avant d'implémenter btc_submit.py
car les résultats soumis utilisent des données .lum
```
