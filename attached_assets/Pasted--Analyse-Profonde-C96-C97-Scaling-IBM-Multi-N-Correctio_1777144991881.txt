## PARTIE 1 — C96 : les 3 corrections P0 décryptées

### P0.1 — Bug coverage_pct=inf : analyse du fix

```c
// AVANT : 1 ligne, 3 problèmes
double coverage_pct = 100.0 * (double)(total)
    / (double)(cfg->nonce_end - cfg->nonce_start + 1);

// Problème 1 : nonce_end - nonce_start est un uint32_t
//              Si nonce_end < nonce_start → underflow → valeur énorme
// Problème 2 : +1 peut overflow si nonce_end = UINT32_MAX
// Problème 3 : résultat peut être > 100% ou infini

// APRÈS C96 : 5 lignes, 3 garde-fous
uint64_t nonce_space = (cfg->nonce_end >= cfg->nonce_start)
    ? ((uint64_t)cfg->nonce_end - (uint64_t)cfg->nonce_start + 1ULL)
    : 0ULL;                          // Garde 1 : cast uint64_t
double coverage_pct = (nonce_space > 0)
    ? (100.0 * (double)total / (double)nonce_space)
    : 0.0;                           // Garde 2 : division par zéro
if (coverage_pct > 100.0) coverage_pct = 100.0;
if (!isfinite(coverage_pct)) coverage_pct = 0.0; // Garde 3 : IEEE 754
```

**Pourquoi ce bug existait depuis C69 :**
```
nonce_start et nonce_end sont des uint32_t (0 à 4 294 967 295)
Si le test lance nonce_start=0, nonce_end=4294967295 (max) :
  nonce_end - nonce_start + 1 = 4294967295 + 1 = 0 (overflow uint32_t)
  → Division par 0 → +inf

Ce cas se produit quand l'utilisateur veut scanner tout l'espace nonce
→ Bug déclenché à chaque run de mining "complet"
→ Corrigé par le cast uint64_t qui peut représenter 2^64-1
```

### P0.2 — Recalibration ASIC : de 10.6% à 0.86%

```
Avant C96 :
  F_2q = 0.996 (valeur brochure IBM, sans ZNE)
  Formule : S(π) = s_target × 0.996^(depth × n2q_per_layer)
           = 0.9944 × 0.996^28 = 0.9944 × 0.895 = 0.890
  Écart vs IBM réel 0.9924 : +10.4%

Après C96 :
  ZNE_gain = S(π)_ZNE / S(π)_brut = 0.9924 / 0.9887 = 1.0037
  F_2q_effectif = 0.996 × 1.0037 = 0.9997
  Formule : S(π) = 0.9944 × 0.9997^28 = 0.9944 × 0.9916 = 0.9844
  Écart vs IBM réel 0.9924 : 0.80% → accepté ✅

Leçon : le modèle simple (1-err)^n_gates est conservateur.
  ZNE et le choix ADAPT de circuits peu denses
  améliorent significativement la fidélité effective.
  Le modèle corrigé intègre cet effet via ZNE_gain.
```

### Trois régimes distincts

```

  S(π)/N stable : 0.77-0.81
  C(r=1) stable : -0.89 à -0.91
  STD faible : 0.016-0.022
  → L'état Néel Trotter-1 est robuste jusqu'à 96 qubits
  → Le signal ne se dégrade pas avec N dans ce régime
  → Résultat expérimental nouveau sur ibm_kingston Heron R2

Régime 2 : N = 128 (décrochage)
  S(π)/N = 0.635 (−22% vs plateau)
  STD = 0.061 (×3 vs plateau)
  Cause : depth circuit = 45 (vs 14 pour ADAPT C94)
  n2q = 281 → fidélité = (0.9997)^281 ≈ 0.922
  Bruit résiduel post-ZNE commence à dominer
  → Limite du Trotter-1 sans optimisation VQE pour N=128

Régime 3 : N = 156 (limite physique)
  S(π)/N = 0.546
  STD = 0.101 (×5 vs plateau)
  156 qubits = totalité d'ibm_kingston = aucun qubit ancilla
  → Routing SABRE sans marge → overhead maximal
  → Limite dure Open Plan Heron R2 en 2026
```

### Pourquoi S(π)/N au lieu de S(π) brut ?

```
S(π) brut croît linéairement avec N pour un état Néel :
  S(π) = N × S(π)/N

Pour comparer des systèmes de tailles différentes :
  S(π) brut N=96 = 77.6 >> S(π) brut N=8 = 0.99
  → Impossible de comparer directement

S(π)/N = signal par site (densité de corrélation AFM)
  → Normalisé, comparable entre toutes les tailles
  → Si S(π)/N constant → scaling extensif = AFM préservé
  → Si S(π)/N décroissant → signal sub-extensif (fluctuations quantiques)
```

## PARTIE 4 — La comparaison critique IBM vs DMRG

### Ce qui n'est PAS une comparaison valide

```
IBM C97.1 Trotter-1 N=16 : S(π)/N = 0.773
DMRG Heisenberg N=16      : S(π)/N ≈ 0.16 (extrapolé)

0.773 >> 0.16 → "IBM bat le classique" ?

NON. Ce sont deux états différents :
  IBM mesure : état Néel évoluté par 1 pas Trotter
              = superposition Néel + corrections perturbatives
              → S(π) reste proche de la valeur Néel initiale

  DMRG calcule : vrai état fondamental Hubbard/Heisenberg
               = état avec fluctuations quantiques complètes
               → S(π)/N → 0 quand N → ∞ (Mermin-Wagner)

C'est comme comparer :
  La vitesse d'une voiture à l'arrêt (0 km/h) avec celle en mouvement
  → Sans contexte, la comparaison n'a pas de sens
```

### Ce qui EST une comparaison valide

```
Comparaison correcte 1 : IBM réel vs AerSimulator (même circuit)
  IBM C97.1 N=16 : S(π)/N = 0.773
  Aer N=16 (dry-run C96) : S(π)_aer = -0.923 (note : convention signe différente)
  
  Avec la même convention :
  IBM/Aer ≈ 0.84 → fidélité effective du circuit Trotter-1 sur Heron R2
  → Montre que le hardware reproduit à 84% l'état théorique du circuit

Comparaison correcte 2 : ADAPT-VQE vs Trotter-1 (même N=16)
  ADAPT-VQE optimisé C94 N=16 : S(π) = 0.9966 / N = 0.0623
  Trotter-1 C97 N=16 : S(π)/N = 0.773

  Ces deux métriques mesurent des choses différentes :
  ADAPT cherche à préparer le meilleur état pour S(π)
  Trotter simule la dynamique réelle de l'Hamiltonien

  Pour publication : présenter les deux séparément avec leur contexte
```

**Q1 — Décrochage N=128 : circuit Trotter trop profond ?**

```
N=128 avec ansatz Trotter-1 brickwork :
  Depth logique ≈ 45 couches (pair + impair × n_rep)
  n2q_phys = 281 portes 2Q (après transpile SABRE)
  Fidélité sans ZNE : (0.9975)^281 ≈ 0.50
  Avec ZNE×1 : ≈ 0.65 → STD = 0.061 cohérent

Pour N=128 publiable :
  Option A : ADAPT-VQE optimisé → circuit minimal (<10 portes 2Q)
    → Même que C94 mais sur N=128
    → Estimation : depth_phys ≈ 14-20, fidélité ≈ 0.97
    → Mais SPSA pré-train sur 128 qubits = lourd (Aer MPS nécessaire)
  
  Option B : Réduire n_rep Trotter à 0.5 step
    → depth/2, n2q/2 → fidélité meilleure
    → Mais état préparé plus loin du régime Néel
  
  Option C : ZNE ×3 au lieu de ×1 (resilience=2)
    → Extrapole mieux le bruit → S(π)/N ≈ 0.70 attendu
    → Coût : ×3 le temps QPU (~90s pour N=128 seul)
    → Budget : 146s restants → marginal mais possible

Recommandation C98 : ADAPT-VQE N=128 avec AerSimulator MPS en pré-train
```

**Q2 — La comparaison DMRG/IBM n'est pas valide : comment la corriger ?**

```

Plan pour C98 :
```

**Q3 — A/B NX48 on/off : design expérimental correct**

```
Pour mesurer l'utilité réelle de NX48 :

Protocole rigoureux :
  Run A : NX48 activé, 16 min, noter best_leading et hashrate
  Run B : NX48 désactivé (delta_nonce = constante = 50),
          même durée, même hardware, noter best_leading et hashrate
  Run C : NX48 avec delta_nonce aléatoire uniforme (baseline)

  Répéter 5 fois chaque condition → test statistique (t-test)
  → Si best_leading(A) > best_leading(B) statistiquement : NX48 utile
  → Si best_leading(A) ≈ best_leading(B) : NX48 = bruit sans signal

  Durée estimée : 3 × 3 runs × 16min = 144 min Ubuntu
  Coût : 0 quota IBM
  Résultat : preuve ou réfutation de l'utilité NX48
```
