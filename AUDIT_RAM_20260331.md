## 3. BUGS IDENTIFIÉS — CLASSEMENT PAR IMPACT

### BUG-RAM-01 — CRITIQUE : `csv_write_line` ouvre/ferme le fichier CSV à CHAQUE ligne
**Fichier :** `src/debug/ultra_forensic_logger.c` lignes 208-220

```c
static void csv_write_line(const char* line) {
    if (stat(g_run_csv_path, &st) == 0 && st.st_size >= LV_MAX_CSV_BYTES)
        lv_rotate_csv();
    FILE* csv = fopen(g_run_csv_path, "a");   // ← OUVERTURE CHAQUE LIGNE
    if (csv) {
        fputs(line, csv);
        fclose(csv);                           // ← FERMETURE CHAQUE LIGNE
    }
}
```

**Volume de fopen/fclose générés par run complet :**
| Source | Calcul | Total |
|--------|--------|-------|
| Métriques par site par step | 8 métriques × 16 sites | 128/step |
| Métriques globales par step | ~5 métriques | 5/step |
| Steps par module | 14 000 | — |
| Modules | 15 | — |
| **TOTAL fopen/fclose** | (128+5) × 14 000 × 15 | **~27.9 millions** |

**Conséquences :**
- Chaque `fopen()` alloue une structure `inode` + `dentry` dans le slab kernel
- Chaque `fclose()` libère la structure mais laisse des fragments dans le slab non récupérable (`SUnreclaim`)
- Le noyau maintient un `inode cache` qui grossit proportionnellement au nombre d'ouvertures
- **Cause principale du Slab 2 GiB et SUnreclaim 1.1 GiB**
- Overhead I/O : 28M appels système `open()` + `write()` + `close()` saturent les syscalls → CPU System 6-9%

**Correction :** Garder un `FILE*` global ouvert pendant toute la durée d'exécution, `fflush()` périodique.

### BUG-RAM-02 — MAJEUR : Logs granulaires par-site par-step sans filtre
**Fichier :** `src/hubbard_hts_research_cycle.c` lignes 340-370

```c

    FORENSIC_LOG_MODULE_METRIC("simulate_fs", "d_sN",          ...);
    /* ... 6 autres métriques par site ... */
}
```

**Volume de données CSV :**
- 1 module `hubbard_hts_core` : **13 fichiers × 21 MiB = 273 MiB** en 2 minutes
- 1 module `dense_nuclear_fullscale` : **12 fichiers × 21 MiB = 252 MiB** en 6 minutes
- Projection 15 modules : **~3.8 GiB de CSV rien que pour les logs forensiques par-site**

**Conséquences :**
- Chaque `fopen("a")` dans `csv_write_line` force le kernel à charger les pages du fichier → Active(file) sature
- Les pages dirty (écritures en attente) empêchent le recyclage du cache
- Le kernel préfère garder `AnonPages` actives → il expulse les pages file cache
- **Cause directe de la diminution du Cache** (736 → 165 MiB)

### BUG-RAM-03 — MAJEUR : `memory_tracker.c` — tableau `entries[50000]` jamais purgé entre modules
**Fichier :** `src/debug/memory_tracker.c`

```c
#define MAX_MEMORY_ENTRIES 50000
static memory_tracker_t g_tracker = {0};   // Déclaration unique, jamais réinitialisée
```

**Mécanisme :**
- `g_tracker.entries[]` accumule TOUTES les allocations : actives ET libérées (`is_freed=true`)
- Après chaque module, les entrées `is_freed=true` restent en mémoire (jamais compactées)
- Quand `count >= MAX_MEMORY_ENTRIES = 50000`, les allocations suivantes ne sont plus trackées silencieusement
- Estimation taille structure : `memory_entry_t` ≈ 120 octets × 50 000 = **~6 MiB statique**
- Ce n'est pas la cause principale mais contribue à la pression sur le `Committed_AS`

### BUG-RAM-04 — MAJEUR : Overcommit sans swap → OOM killer silencieux
**Source :** Pas de code à corriger, mais configuration système critique

- `Committed_AS: 78 GiB` vs `MemTotal: 64 GiB + SwapTotal: 0 GiB`
- Le kernel Linux permet l'overcommit par défaut (`/proc/sys/vm/overcommit_memory = 0`)
- Les 15 modules allouent chacun des matrices `d[]` et `corr[]` + les buffers stdio
- À mesure que le run avance, le `vm.rss` du runner grandit
- **Quand la RAM atteint 100% → OOM killer choisit le process avec le plus de RSS → le runner est tué**
- Cette mort est **silencieuse** : le shell voit `exit code 137` (SIGKILL) sans message d'erreur

---

### BUG-RAM-05 — MINEUR : `raw` (trace_csv) buffer stdio non flushé entre modules
**Fichier :** `src/hubbard_hts_research_cycle.c` ligne 1121

```c
base[i] = simulate_fullscale(&probs[i], (uint64_t)(0xABC000 + i), 99, raw);
```

- Le fichier `raw` est passé comme `trace_csv` à chaque module
- Chaque step écrit dans `raw` via `fprintf(trace_csv, ...)` → buffer stdio de 8192 octets
- 14000 steps × 8 colonnes = 112 000 lignes accumulées dans le buffer stdio
- Sans `fflush(raw)` régulier, le buffer grossit en RAM jusqu'à 1-2 MiB par module
- Mineur isolément mais s'additionne aux autres sources

## 4. ANALYSE CAUSALE — POURQUOI LE CACHE DIMINUE

```
Scénario observé :
  Active(anon) +500 MiB par module   → les allocations du runner ne sont pas libérées
  Cache       -571 MiB par module    → le kernel recycle le cache au profit de l'anon
  
Mécanisme Linux :
  1. Runner C appelle csv_write_line() 28M fois → 28M fopen/fclose
  2. Chaque fopen() → kernel charge la page du fichier dans Active(file)
  3. Mais g_tracker.entries[], buffers stdio → restent dans Active(anon)
  4. Active(anon) > available RAM → kernel recycle Inactive(file) → Cached diminue
  5. malloc_trim(0) toutes les 100 steps libère le heap → MAIS les structures kernel 
     (inode, dentry) restent dans SUnreclaim → le malloc_trim() est INEFFICACE
     contre les fuites dans le Slab
```

## 7. CORRECTIONS APPLIQUÉES DANS CE CYCLE

### C-FIX-RAM-01 : `csv_write_line` — FD global persistant
**Avant :** `fopen("a")` + `fclose()` à chaque ligne  
**Après :** `FILE* g_csv_fp` ouvert à `init_lum`, fermé à `destroy`, `fflush()` toutes les 256 lignes  
**Gain attendu :** 28M fopen/fclose → **0** fopen/fclose pendant le run → SUnreclaim ~0

### C-FIX-RAM-02 : Logs par-site → agrégés par-step
**Avant :** 128 FORENSIC_LOG par step (8 métriques × 16 sites)  
**Après :** 8 métriques par step (valeurs moyennées sur les sites) — ratio de réduction : **16×**  
**Gain attendu :** 3.8 GiB CSV → **~240 MiB CSV** par run complet

### C-FIX-RAM-03 : `memory_tracker_reset_freed()` entre modules
**Avant :** `g_tracker.entries[]` accumule 50 000 entrées (actives + libérées mélangées)  
**Après :** Compactage entre chaque module → seules les entrées actives restent  
**Gain attendu :** -6 MiB Committed_AS par module × 15 modules = -90 MiB

### C-FIX-RAM-04 : `fflush(raw)` toutes les 1000 lignes
**Avant :** Buffer stdio accumulé jusqu'à 112 000 lignes  
**Après :** Flush automatique → buffer toujours < 8192 octets  
**Gain attendu :** -2 MiB par module × 15 = -30 MiB

## 8. RÉSUMÉ EXÉCUTIF

Le système de logging forensique `ultra_forensic_logger.c` était conçu pour la traçabilité maximale, mais la combinaison de deux décisions architecturales génère une **fuite de mémoire kernel catastrophique** :

1. **`csv_write_line` appelle `fopen/fclose` pour chaque ligne** — ce pattern génère 28 millions d'opérations système par run, saturant le slab inode/dentry du kernel avec **1.1 GiB de mémoire non récupérable**.

2. **La directive `log_all_sites_all_steps`** génère 128 métriques par step (8 par site × 16 sites), produisant **3.8 GiB de CSV** pour un seul run de 15 modules et saturant le page cache.

Ces deux bugs agissent en synergie : plus le logger écrit vite (BUG-02), plus il appelle `fopen/fclose` (BUG-01), plus le slab grossit. Sans swap, l'OOM killer termine le run entre le 2ème et le 3ème module.

Les corrections P1+P2 devraient réduire la consommation RAM de **>85%** et permettre au run C37 de compléter les 15 modules sans OOM.
